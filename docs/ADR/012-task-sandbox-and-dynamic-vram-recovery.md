# [ADR-012] 단일 노드 추론 안정성을 위한 Task 샌드박스 격리 및 동적 VRAM 회수 아키텍처 도입

* **Status:** Accepted
* **Date:** 2026-07-28
* **Related Documents:** [Backend_devlog.md](../devlogs/Backend_devlog.md)

## 1. Context (배경)

단일 노드 서버(FastAPI)에서 음원 분리(Demucs)와 피치 추적(CREPE) 파이프라인을 운영할 때 인프라 제약이 발생했다[cite: 2].
1. **경쟁 상태 (Race Condition):** 임시 파일들이 단일 디렉토리에 공유되면서 다중 요청 시 파일 I/O 충돌 및 덮어쓰기 위험이 노출되었다[cite: 2].
2. **VRAM 파편화:** 지연된 파이썬 가비지 컬렉션(GC)으로 인해 추론 중 VRAM이 파편화되어 간헐적인 OOM(Out of Memory) 크래시가 유발되었다[cite: 2].
3. **이벤트 루프 지연:** 무거운 동기 프로세스 호출이 비동기 메인 루프를 블로킹하여 서버 응답성을 저하시키는 문제가 관찰되었다[cite: 2].

## 2. Decision (결정)

안정적인 자원 관리 및 데이터 무결성 보호를 위해 다음과 같이 서버 아키텍처를 구성한다.

1. **Task Sandbox 격리:** 모든 요청에 고유한 `task_id`를 발급하고, `outputs/{task_id}/` 구조의 격리된 샌드박스 디렉토리 내에서만 I/O를 수행하도록 제한한다[cite: 2].
2. **동적 배치 사이징 및 VRAM 회수:** 추론 루프 내부에 `try-except RuntimeError` 블록을 배치하여 OOM 발생 시 배치를 절반으로 줄여 재시도하는 동적 백오프(Dynamic Backoff)를 적용하고, 에러 시 명시적인 `gc.collect()`와 `torch.cuda.ipc_collect()`를 호출한다[cite: 2].
3. **스레드풀 위임:** 서브프로세스 생성에 따른 OS 의존성 및 블로킹을 방지하기 위해, 외부 라이브러리 실행을 `loop.run_in_executor`를 활용한 외부 스레드풀로 오프로딩한다[cite: 2].

## 3. Rationale (의사결정 근거)

### 3.1. Thread-safe 달성과 오버헤드의 트레이드오프
요청별 디렉토리 생성 및 삭제는 디스크 I/O 레이턴시를 소폭 증가시키나, 세션 데이터 교차 오염을 방지하기 위한 필수적인 방어 수단이다.

### 3.2. 최대 처리량 보존을 위한 동적 대응
초기부터 배치 사이즈를 최소화하여 OOM을 피하는 방식은 평상시의 GPU 병렬 연산 이점을 포기하게 만든다. 동적 배치 감축 방식은 한계 지점까지 추론 속도를 유지하면서 안정성을 확보하기 위한 현실적인 대안이다.

## 4. Consequences (결과)

* **Positive:** 파일 교차 오염을 방지하며, OOM 발생 시 자가 복구를 시도하여 파이프라인 중단 빈도를 낮출 수 있다.
* **Negative:** 파일 시스템 접근 및 명시적 GC 호출 횟수 증가로 인해 단일 요청 처리의 오버헤드가 누적될 수 있다.
