# [ADR-0003] 피치 트래킹 엔진 전면 교체 및 VRAM 추론 최적화 아키텍처 도입

* **Status:** Accepted
* **Date:** 2026-03-03
* **Category:** Core Algorithm / ML Engineering

## 1. Context (배경)

Phase 1 파이프라인에서는 베이스 피치(f0) 추출을 위해 전통적인 DSP 알고리즘인 `librosa.pyin`을 사용했다. 그러나 베이스 오디오는 저음역대의 배음(Harmonics) 구조가 복잡하고, Demucs 분리 과정에서 미세한 아티팩트(Artifact)가 섞여 있어, 수학적 자기상관함수(Autocorrelation)에 의존하는 pYIN 알고리즘은 잦은 옥타브 에러와 인식률 저하를 보였다.

이를 해결하기 위해 CNN 기반의 SOTA 딥러닝 피치 트래커인 `torchcrepe`를 도입했으나, 다음과 같은 심각한 시스템 엔지니어링 문제에 직면했다.

1.  **CUDA OOM (Out of Memory):** 3~5분 길이의 오디오 전체를 한 번에 텐서(Tensor)로 변환하여 GPU에 올리면 VRAM 한계를 초과하여 서버가 다운된다.
2.  **메모리 팽창 (Float Bloat):** 전처리 단계에서 `scipy.signal.butter` 필터를 거친 오디오 배열은 기본적으로 `float64`(배정밀도)로 변환된다. 이를 그대로 PyTorch 모델에 주입하면 연산 속도가 저하되고 VRAM 점유율이 2배로 폭증한다.
3.  **유연성 부재:** 무거운 `full` 모델이 하드코딩되어 있어 빠른 프로토타이핑 테스트 시 극심한 병목(10분 이상 소요)이 발생했으며, Apple Silicon(M1/M4) 등 로컬 Mac 환경에서의 하드웨어 가속(MPS)이 지원되지 않았다.

## 2. Decision (결정)

피치 트래킹 엔진을 `torchcrepe`로 전면 교체하며, 안정적인 모델 서빙을 위해 다음과 같은 **VRAM 추론 최적화 아키텍처**를 파이프라인에 강제한다.

1.  **명시적 다운캐스팅:** `scipy` 필터링 직후 오디오 배열을 `numpy.float32`로 강제 변환한다.
2.  **청크 분할 (VRAM-Safe Chunking):** 오디오 텐서를 30초 단위(`chunk_duration=30`)로 분할하여 추론하고, 루프마다 `del`과 `torch.cuda.empty_cache()`를 호출하여 VRAM 피크(Peak) 부하를 평탄화한다.
3.  **동적 디바이스 할당 및 모델 스케일링:** `cuda`, `mps`, `cpu`를 동적으로 인식하는 분기 로직을 추가하고, 파라미터로 `model_capacity`를 외부로 노출하여 개발/테스트 시에는 고속 추론을 위한 `tiny` 모델을, 프로덕션에서는 `full` 모델을 사용할 수 있도록 결합도를 낮춘다.

## 3. Rationale (의사결정 근거)

### 3.1. 정확도와 노이즈 저항성 (CREPE > pYIN)
`torchcrepe`는 대량의 오디오 데이터로 학습된 CNN 모델이므로, 신호에 노이즈나 타 악기의 블리딩이 미세하게 섞여 있더라도 기음(Fundamental Frequency)을 찾아내는 생존율이 pYIN보다 압도적으로 높다. 특히 디코더로 `Argmax`를 사용하면 Viterbi 디코딩보다 노이즈 스파이크 환경에서 더 강건한(Robust) 결과를 낸다.

### 3.2. Float32 다운캐스팅의 공학적 타당성
오디오 딥러닝 추론에서 `float64`의 극단적인 정밀도는 실질적인 피치 추적 해상도 향상에 아무런 기여를 하지 못한다. 이를 `float32`로 낮추는 것은 정보 손실이 아닌 '비용 정상화'이며, 메모리 풋프린트를 즉시 50% 절감하여 배치 사이즈(`batch_size`)를 늘릴 수 있는 여유 공간을 확보해 준다.

### 3.3. Chunking 아키텍처의 필수성
입력 오디오 길이가 N일 때 주의(Attention) 매커니즘이나 대형 CNN 계층을 통과하면 활성화 함수(Activation) 메모리가 N에 비례하거나 그 이상으로 팽창한다. 제한된 서버 환경(예: 16GB VRAM의 T4 GPU)에서 OOM 없이 안정적으로 서비스를 운영하려면 물리적인 청크 분할을 통한 메모리 가비지 컬렉션(GC)이 유일하고 확실한 방어책이다.

## 4. Consequences (결과)

* **Positive:**
    * 오디오의 길이에 상관없이 일정한 VRAM 점유율(안정적인 플래토)을 유지하여 OOM 에러를 원천 차단했다.
    * `float32` 다운캐스팅과 `tiny` 모델 채택으로 추론 속도가 기존 10분대에서 1분 이내로 비약적으로 단축되어 개발 주기(Iteration)가 가속화되었다.
    * MPS 지원으로 클라우드 종속성 없이 로컬 Mac에서도 GPU 가속 테스트가 가능해졌다.
* **Negative (Mitigated):**
    * 오디오를 청크로 자를 때 모델 내부의 합성곱 패딩(Padding) 로직으로 인해 끝단 프레임이 잘려 나가거나 밀리는 현상이 발생할 수 있다.
    * **Mitigation (완화):** 이를 방지하기 위해 청크 사이즈를 반드시 `hop_length`의 배수로 정렬하고, 마지막 청크가 모델 요구 최소 샘플(1024)보다 작을 경우 Constant Padding을 추가한 뒤 병합 후 정확한 인덱스로 재절사(Truncation)하는 방어 로직을 코드에 포함시켰다.
